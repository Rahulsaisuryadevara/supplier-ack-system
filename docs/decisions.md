# Design decisions, assumptions, trade-offs, and limitations

- **Python 3.11+:** accessible ecosystem and straightforward local execution; not intended as a high-throughput distributed service.
- **pandas:** concise deterministic synthetic-data generation and evaluation; memory use grows with dataset size.
- **SQLite:** free, serverless persistence for a single-candidate challenge; write concurrency is limited compared with server databases.
- **argparse:** standard-library CLI with no runtime framework dependency; more manual work than Typer for complex commands.
- **pytest:** expressive regression tests for conditional business rules; tests must be kept aligned with evolving policies.
- **Synthetic data:** generated records are fictional and should not be represented as real supplier performance.
- **Approval policy:** percentage and date-slip thresholds are configurable. The workflow should preserve the original request, decision, approver, and reason.
- **Actors:** Supplier owns acknowledgements and change requests; Planner owns schedule updates; Carrier/Warehouse Operator confirms physical milestones; Logistics Analyst assesses transit risk; Operations Manager approves escalations.
- **Implementation status:** the relational SQLite schema, foreign-key constraints, append-only event log, bridge tables, schema-level guards, seeded master-data generation, acknowledgement/promise revisions, rule-driven change requests and approvals, coverage reporting, and supplier-silence chase notifications are implemented. Inventory-plan/production-order generation and the end-to-end runtime workflow remain later stages.
- **Deterministic ID nomenclature:** `IDFactory` fixes the challenge year at `2026`, uses global six-digit counters for Supplier, PurchaseOrder, Notification, and ProductionOrder, and parent-scoped counters for child/revision IDs. Two-digit counters are capped at 99 and six-digit counters at 999999; exhaustion raises `OverflowError` rather than widening IDs beyond the exact contract. Counters can be snapshotted/restored as JSON, but issued IDs have no mutation API.
- **Approval ID format:** chose `APR-<full change_request_id>-NN`, for example `APR-CHG-PO-2026-000001-000001-01`. Although longer than using only the change sequence, it embeds the complete immutable parent key and makes approvals globally interpretable without a lookup. This is the exact format used by `IDFactory` and the schema validators.

## Seeded master-data generation distributions (Generation Steps 2 and 4)

- **Single RNG stream:** the CLI constructs exactly one `numpy.random.Generator` with `default_rng(seed)` in `generators/framework.py`; each generation function receives that object. Entity modules do not import or initialize global random generators. The default seed is `20261022`; the CLI `--seed` override is recorded in `generation_summary.json`.
- **Scale parameters:** `starter` configures 40 suppliers and 200 POs; `full` configures 200 suppliers and 10,000 POs. Both use the same functions and schema contracts. The item catalog is 50 items on both scales; reference counts and actor-role counts are configured by scale.
- **Supplier lead time:** 82% of suppliers draw an inclusive integer from 7–30 calendar days and the remaining 18% draw from 31–90. This gives a common operational band and a meaningful long-lead tail. Each PO required-delivery date is `order_date + supplier.lead_time_days + buffer`, where the buffer is an inclusive 2–7 calendar days. PO creation dates are sampled from business weekdays between 1 January and 30 June 2026; this is a weekday calendar, not a country-specific public-holiday calendar.
- **Supplier reliability:** 92% of suppliers draw `Beta(8, 2)`, producing a distribution concentrated toward high reliability; the 8% low-reliability cohort draws `Beta(2, 5)`, so the synthetic population contains a small but identifiable weaker-performing tail. Scores are clipped to `[0.01, 0.9999]` and rounded to four decimal places to avoid degenerate exact boundaries.
- **On-time rate correlation:** on-time rate is constructed as `0.60 × reliability_score + 0.40 × Beta(8, 2) noise`, clipped to `[0.01, 0.9999]` and rounded to four decimals. This encodes a deliberate positive relationship while retaining supplier-specific variation; it is not sampled independently. Generation reports the observed Pearson correlation as a quick diagnostics metric rather than assuming a fixed sample correlation.
- **Supplier status:** `ACTIVE 94%`, `ON_HOLD 4%`, `BLOCKED 1.5%`, and `INACTIVE 0.5%`. The slight inactive/blocked tail gives downstream workflow scenarios realistic suppliers that may need operational attention. Supplier `risk_tier` is derived from reliability score thresholds: LOW at >=0.85, MEDIUM at >=0.65, HIGH at >=0.40, otherwise CRITICAL.
- **Supplier weighting across POs:** supplier selection uses randomly permuted Pareto rank weights with exponent `alpha=1.15`, normalized to probabilities. This produces a long-tail distribution where some suppliers receive many more orders than others without tying high volume to low supplier IDs. The alpha value is configurable.
- **Preferred carriers:** supplier preferences use a mild carrier popularity skew (`rank^-0.7`). For a PO, the supplier preferred carrier is selected with probability 0.78; otherwise a carrier is sampled from the carrier master. These parameters are configurable and make the carrier preference field operationally meaningful.
- **PO line counts:** each PO has an inclusive uniform line count from 2 to 6. This provides variation and an expected value of 4 lines per PO (about 800 lines starter and 40,000 full, with a valid random range of 400–1,200 and 20,000–60,000 respectively).
- **Quantity distribution:** requested line quantities are sampled from a log-normal distribution with `mean=5.8` and `sigma=0.85`, clipped to the configured inclusive range 10–5,000 and rounded to three decimal places. A log-normal distribution captures many moderate orders with a right tail of larger industrial quantities, unlike a uniform distribution that would overproduce very large quantities.
- **Item master and pricing:** the synthetic catalog contains 50 fixed, fictitious industrial items across fasteners, bearings, electrical, fluid-handling, and packaging categories. Each category's configured price bounds are used to create a per-item min/max price band; line unit prices are sampled only within the selected item's band and rounded to two decimals. The initial currency is configurable and defaults to INR. The data contains no real supplier or market pricing.
- **Derived totals:** `POLine.line_total` is computed with decimal `ROUND_HALF_UP` rounding from `requested_qty × unit_price`. The initial PO header generator carries a temporary zero value because line records do not yet exist; the orchestration framework replaces `PurchaseOrder.total_order_value` with the sum of its computed line totals after POLines are generated. No PO total is sampled independently.
- **Reference actors and IDs:** all actor names, supplier names, emails, item names, warehouse names, and carrier names are synthetic. `Supplier`, `PurchaseOrder`, and `POLine` IDs are issued using the shared `IDFactory`; supporting master IDs use their documented sequential support-table prefixes. Master rows are validated against schema metadata and parent references before export.


## Acknowledgement and change-event coverage profile (Generation Step 4)

- **Event-count semantics:** `scales.*.event_count` counts acknowledgement rows (including every retained revision) plus ChangeRequest rows. Approval decisions and PromiseDate revision rows are separate dependent records and do not consume this explicit 15,000/300 event budget. The generator fills the remaining event budget with ChangeRequest rows after allocating acknowledgement revisions.
- **Target mix and denominators:** partial acceptance (22%), full acceptance (70%), and full rejection (8%) are measured among responding POs (supplier-silence POs are excluded). Date slips (30%) and on-time promises (70%) are measured among current line-level PromiseDate rows. Price changes (6%) are measured among lines with positive acknowledged quantity. Supplier silence (5%) and multiple acknowledgement revisions (8%) are measured against all POs. These denominators are intentionally different because each metric answers a different operational question. Integer targets use deterministic nearest-integer rounding; small starter datasets therefore show small percentage deviations.
- **Supplier silence:** 5% of POs are selected using a risk score weighted toward lower reliability, large total line quantities, and a small Gaussian noise term. A silent supplier has no Acknowledgement row at all; its original `response_due_at` is checked against the configured `coverage.as_of_date` and the exception is emitted to `silence_report.csv` with `MISSING_ACK` on both `issue_type` and `ground_truth`. This avoids misleading fabricated empty response rows.
- **Acknowledgement outcomes:** POs are risk-ranked before exact outcome counts are assigned: full rejection goes to the highest-risk group, partial acceptance to the next-highest, and full acceptance to the remainder. Risk combines `0.76 × (1 − reliability_score)`, `0.20 × z(log(PO total quantity))`, and configurable normal noise (`risk_noise_sd=0.12`). This makes less reliable suppliers and larger orders more likely to have adverse outcomes while keeping the headline proportions stable.
- **Partial quantities and reasons:** a line's accepted/requested ratio is Beta-distributed with configurable concentration 10. The expected share declines for lower supplier reliability and large quantities; the mean is clipped to 20%–96% so a partial row cannot accidentally become full acceptance or full rejection after rounding. The rejected quantity is calculated as requested minus accepted. A rejection reason is weighted categorical: capacity 34%, stock 34%, logistics 18%, and price 14%; only partial/full-rejection responses require a reason. Quantities are rounded to 3 decimals and reconciled exactly.
- **Promised dates:** 30% of currently promised lines are risk-ranked toward lower reliability and higher quantities. Slip days follow a log-normal distribution (`mean=1.90`, `sigma=0.60` in log space), rounded and clipped to 3–60 calendar days, concentrating most slips in the 3–14 day band while retaining a longer tail. The remaining 70% use early-day offsets from a Beta(2,5) distribution scaled to 0–5 days, with promise dates constrained not to predate the revision's effective date. Promise rows are retained per accepted line per acknowledgement revision, with `superseded_by` chains; only the latest row is `CURRENT`.
- **Price changes:** 6% of lines with positive acknowledged quantities are selected by line-risk rank (larger quantities and lower reliability increase selection weight). Magnitudes map a Beta(2,3.5) draw to 0.5%–15%; 78% are configured as increases and 22% as decreases. Values are rounded to cents, and the change is represented by a `PRICE_CHANGE` request with previous and requested prices. `acknowledged_unit_price` retains the supplier's quote; after a rejected approval, `projected_unit_price` remains at the original PO price so a rejected proposal does not silently alter the projected financial plan.
- **Multiple revisions:** 8% of all POs are targeted, selected among responders if necessary. Such POs receive 2–4 independent Acknowledgement rows with revision counts chosen from 2 (50%), 3 (35%), and 4 (15%). Older rows are marked `SUPERSEDED` and point forward via `superseded_by`; their payloads are retained. Each revision gets its own line-level PromiseDate rows and promise supersession chain.
- **Change request values and deltas:** every generated request is based on source data. Price changes compare the requested PO unit price with the supplier-quoted unit price; quantity changes compare the PO-line requested quantity with the latest acknowledged accepted quantity; date changes compare the requested line date with the current PromiseDate. `old_value` and `new_value` retain those values as text, while `delta` is computed as a signed percentage for price/quantity or signed calendar days for dates. A quantity shortfall is therefore represented as a negative quantity percentage, and threshold evaluation uses its absolute magnitude.
- **Configured threshold routing:** `config/generator_config.yaml` defines planner thresholds of ±5% for unit price, 7 calendar days for positive date slip, and ±10% for quantity change. A change within its threshold receives a planner Approval row with a deterministic `APPROVED` decision. A change beyond the threshold receives a planner `ESCALATED` row followed by an operations-manager Approval row. Changes beyond the configured hard policy limits (15% absolute price, 30 days positive date slip, or 50% absolute quantity change) are deterministically rejected by the final required approver; there is no random approval probability. A date slip greater than 7 days is tagged `DATE_SLIP_REQUIRES_APPROVAL` and carries `downstream_impact_flag=true` in the event payload for downstream planning.
- **Approval and application gate:** Approval records are append-only in the SQLite schema; updates and deletes are rejected by triggers. A new approval round represents an appeal or later decision, preserving prior decisions. The pure `can_apply(change, approvals)` function returns a `(bool, reason)` pair and permits application only when the latest decision at the required level is `APPROVED`. `change_requested`, `approval_decided`, `change_applied`, and related status-change events provide the audit trail. The legacy ChangeRequest statuses map to the conceptual lifecycle as `SUBMITTED` = open, `UNDER_REVIEW` = pending approval, event state `APPROVED`/`REJECTED` = decision, and `IMPLEMENTED` = applied.
- **Supplier-silence escalations:** if `response_due_at` has passed and no acknowledgement exists, the generator creates a date-type ChangeRequest owned by a planner, retains it in `UNDER_REVIEW` with a pending planner Approval, and emits a sent email chase notification. The request intentionally does not fabricate a promise date; old/new date values remain the originally requested delivery date and delta is zero until a supplier response provides a real commitment. Silence changes stay outside normal auto-approval/application.
- **Change-request event mix:** price-change requests retain the 6% coverage target among lines with positive acknowledged quantity. After those price requests, mandatory supplier-silence date requests are reserved; the remaining event budget is split between non-silence quantity and date requests according to `coverage.change_requests.non_price_type_weights` (50%/50% by default). Cancellation changes are not emitted by the current generator. All approval outcomes are rule-derived rather than sampled independently.
- **Infeasible configuration handling:** `validate_coverage_config()` rejects malformed probability sums and proportions outside [0,1]. It emits runtime warnings when requested multiple-revision POs outnumber responding POs, or the event budget cannot fit the minimum acknowledgement rows implied by silence/revision targets. Actual generation also warns and clips price-change requests if they exceed the remaining change-request budget.
- **Observed default-seed baseline:** seed `20261022` yields 200 starter POs, 214 acknowledgement revisions, 86 ChangeRequests (300 counted events), 669 PromiseDates, 128 Approval rows, 10 sent silence-chase Notifications, and 675 total entity events. Starter ChangeRequest types are date 28 (including 10 silence escalations), price 40, and quantity 18. There are 34 ordinary planner-only routes, 42 operations-manager routes, and 10 silence requests left pending; Approval statuses are `APPROVED=75`, `ESCALATED=42`, `PENDING=10`, `REJECTED=1`. Escalations are date 9, price 24, and quantity 9. For full scale, default seed yields 10,000 POs, 10,803 acknowledgement revisions, 4,197 ChangeRequests (15,000 counted events), 34,097 PromiseDates, 6,188 Approval rows, 500 sent silence-chase Notifications, and 33,252 total entity events. Full-scale ChangeRequest types are date 1,335, price 2,026, and quantity 836; there are 1,706 ordinary planner-only routes, 1,991 operations-manager routes, and 500 silence requests left pending. Approval statuses are `APPROVED=3,670`, `ESCALATED=1,991`, `PENDING=500`, `REJECTED=27`; escalations are date 417, price 1,156, and quantity 418. Seed/config changes may change child-row counts, while the configured acknowledgement-plus-ChangeRequest event budget remains exact.


## Projected supply and downstream impact workflow (Generation Step 6)

- **Baseline-first inventory projection:** every PO line receives InventoryPlan version 1 from its original requested quantity and required date (`source=po_baseline`). A later row is emitted only for a processed acknowledgement with a positive line promise and with no pending/rejected/otherwise-unimplemented change for that line. An acknowledgement-only promise uses `approved_ack`; a change-driven projection uses `approved_change` and points to its implemented ChangeRequest.
- **Approval hard gate:** a pending or rejected change never updates projected supply. If a line has any non-implemented change request, the current projection remains the last safe effective version. The generator intentionally prefers conservative hold behavior where concurrent changes could otherwise partially leak into a projection.
- **Append-only plan versions:** each new InventoryPlan row links to its predecessor with `previous_version_id`; exactly one row per PO line is marked effective and history rows are not updated/deleted. The current generator writes final supersession metadata as part of a version snapshot, and SQLite triggers reject InventoryPlan UPDATE/DELETE operations.
- **Production-order allocation:** a production_order_line bridge records allocated quantity and UOM. The starter and full scales create a configured cohort of production orders, with impacted lines prioritized so the deterministic rules are observable in the sample data.
- **Impact trigger:** a date conflict is recorded only for an implemented date change whose new projected receipt is later than a production order's required-by date plus configured `downstream_impact_tolerances.date_conflict_grace_days`. A quantity shortfall is recorded only when allocated quantity exceeds new projected supply by more than configured `quantity_shortfall_pct`. Pending/rejected changes cannot cause impact rows.
- **Severity:** `compute_impact_severity(slip_days, shortfall_pct)` is a pure function that returns the worse of two bands. Date conflict is LOW through 2 days, MEDIUM through 7, HIGH through 14, CRITICAL beyond 14; quantity shortfall is LOW through 5%, MEDIUM through 10%, HIGH through 25%, CRITICAL beyond 25%. Severity and impact type are computed from source plan/order values, not sampled labels.
- **Schedule mutation and audit:** date conflicts move `planned_start_date` to no earlier than one day after the new projected receipt and set status `RESCHEDULED`; a quantity shortfall sets `AT_RISK` unless an existing higher-priority rescheduled/delayed status is retained. Each status transition and impact is captured as an entity_event attributed to planner or operations manager according to computed severity.

## Notification and traceability policy (Generation Step 7)

- `Notification` separates send/delivery status from `read_status` and includes a template type, severity, rendered subject/body, related entity, PO/ACK/ChangeRequest links where applicable, and append-only recipient rows in `notification_recipient`.
- A PO's owning planner is always read from `PurchaseOrder.planner_actor_id`; change-raised, plan-updated, and downstream-impact notices do not select an arbitrary planner. Approval-decision notices route to the original requester. Plan-update notices fan out to that planner and a logistics analyst; date-slot impacts additionally notify the carrier/warehouse operator. Supplier silence routes a chase to the PO's planner and supplier contact; weekly summaries go to each configured operations manager.
- Every emitted notification adds an entity_event audit row. `trace(not_id, frames)` resolves the notification to its ChangeRequest when present, the related acknowledgement when one exists, the PurchaseOrder, and Supplier. A supplier-silence case is explicitly reported as `complete_supplier_silence` with no ACK rather than fabricating a missing acknowledgement; a notice triggered by an acknowledgement without a ChangeRequest is `acknowledgement-only`.
- **Derived-value single source of truth:** `rules/derived.py` owns monetary rounding, PO totals, acknowledgement deltas/status, promise lateness, threshold-derived change fields, current approved plan selection, production risk metrics, supplier performance scores, and notification impact counts. The generator runs `reconcile()` as a hard post-generation gate; clean datasets must reconcile to zero mismatches before they can be written.
- **Allocation and reconciliation invariant:** a confirmed production order may not allocate more material than its effective projected supply. An over-allocation is permitted only while the order is explicitly `AT_RISK` or `DELAYED`; the shortage is computed as `max(allocated_quantity - projected_qty, 0)`. Event state snapshots are also checked against the documented entity lifecycle transition table.


## Controlled edge-case injection and ground-truth separation (Generation Steps 5 and 7)

- **Two-stage contract:** The generator creates and validates the ordinary baseline, then reconciles its derived fields to zero mismatches. Only after those gates pass does `generators/anomalies.py` inject the configured edge-case cohort using the existing seeded NumPy RNG stream. Clean-baseline reconciliation is retained in `suppliers.attrs["reconciliation_report"]`; injected records are expected to violate the labelled rule and are not silently “fixed” by the clean-data reconciler.
- **Configured counts:** `config/generator_config.yaml` specifies exact per-class counts independently for each scale: 5 of each required class in starter and 25 of each class in full. Generation fails closed if it cannot construct the configured number of targets. Given the same seed and configuration, target selection and identifiers are deterministic.
- **`UNAPPROVED_CHANGE_UPDATES_PLAN`:** A new effective `approved_change` InventoryPlan version references a ChangeRequest with no `APPROVED` Approval. This breaks the approval-before-projection gate. Ground truth expects the invalid version to be reverted and the prior approved plan retained; severity is CRITICAL.
- **`ACK_WRONG_PO_LINE`:** Controlled cloned acknowledgement-line records reference either a PO line belonging to a different PO or a deliberately nonexistent line ID. The record remains labelled internally, and ground truth says to reject the reference rather than silently rewrite an unrelated PO or line; severity is HIGH.
- **`PROMISE_DATE_BEFORE_ORDER_DATE`:** Controlled PromiseDate clones have a promised date earlier than their parent PO order date. They break the temporal validity rule and must be flagged/rejected until a valid date is supplied; severity is HIGH.
- **`STALE_REVISION_OVERWRITE`:** For a PO line with multiple promise revisions, the older/lower revision is marked CURRENT while a newer revision exists and is marked superseded. This breaks revision ordering; the higher revision must win; severity is HIGH.
- **Valid threshold boundaries:** The same post-baseline stage records one exact full-acceptance quantity boundary, exact positive and negative price-threshold cases, and an exact date-slip-threshold case. These are not anomalies: their ground-truth rows have `boundary=true`, no anomaly `issue_type`, and expected planner-level handling because thresholds are inclusive.
- **Ground-truth records:** `ground_truth.csv` and `ground_truth.json` contain one row per injected anomaly plus exact boundary cases, an expected threshold decision for every ChangeRequest, and expected status/severity for every impacted ProductionOrder. `related_entity_ids` provides explicit lineage for each label.
- **Leakage rule:** `issue_type`, `ground_truth`, and any internal `boundary` marker are stripped from every exported input CSV. JSON event payload/state snapshots have those label keys removed too. The export writer verifies every non-target CSV header and raises if a label column leaks. The separate target ground-truth files are intentionally exempt and must never be used as model input features.

## Runtime workflow engine decisions

- The live engine is a transactional SQLite adapter, not a second generator. It imports threshold and derived functions directly from `supplier_ack.rules.thresholds` and `supplier_ack.rules.derived`; approval level and delta are recalculated from source values on every relevant event.
- `runtime_processed_event.event_id` is the idempotency key. Duplicate input event IDs are ignored; business state and audit changes are committed together. If processing fails, the business transaction rolls back and a durable `RUNTIME_EVENT_FAILURE` exception is stored separately.
- Every input produces an `entity_event` receipt. Detailed state-change events are additional append-only records. Runtime exception and decision records are stored in separate append-only tables, each with rule ID, values/trace, severity or approver, and processing timestamp.
- An `ack_submitted` event can create acknowledgement, acknowledgement-line and promise history, and may raise change requests, but it never creates an InventoryPlan version. Only `approval_decision` calls the shared `can_apply()` gate and can append an effective plan version. A caller-supplied `attempt_plan_update` is explicitly refused if there is no approved row at the required level.
- Approval levels are always recomputed with `required_approval_level()` from the configured threshold policy. A decision at the wrong level is rejected and logged. Hard-limit breaches are rejected according to `evaluate_threshold()`; they are not randomly accepted.
- A promise date before `PurchaseOrder.order_date` is rejected, the acknowledgement is marked `EXCEPTION`/`REJECTED`, and the planner is notified. An old revision is retained as a refusal/exception event and never becomes the effective acknowledgement.
- `silence_timeout` creates a planner-routed date chase request and notifies both the owning planner and supplier. Plan changes notify the planner and logistics analyst; downstream delivery-slot impacts also notify the relevant carrier/warehouse operator when available.
- Runtime `created_at`/decision timestamps use wall-clock time because they describe actual processing. These timestamps are not part of offline generated input records; the generator's historical timestamps remain seeded and reproducible.


## CLI error handling and full-scale performance benchmark

The unified `supplier-ack` / `python -m supplier_ack.cli` interface uses argparse for typed seeds and enumerated scales, validates required paths before loading, and converts runtime input/IO errors to concise command errors rather than Python tracebacks. Workflow SQLite connections enable `PRAGMA foreign_keys=ON` and reject database schemas that omit required foreign-key declarations. The `scripts/demo.sh` walkthrough copies the committed `data/samples/demo.db` to a disposable temporary database before processing events, keeping the seed demo reusable.

Measured on 2026-10-28 in this environment (Python 3.13.5, pandas 2.2.3, NumPy 2.3.5, PyYAML 6.0.3, matplotlib 3.10.8; Linux x86_64), with the full-scale configuration of 10,000 POs and 15,000 acknowledgement-plus-change events:

| Stage | Wall time | Peak RSS | Measurement notes |
|---|---:|---:|---|
| Generation core + writing source CSVs | 33.56 s | 725,232 KiB | Seed 20261022; 926,962 derived checks with zero mismatches |
| CSV validation | 12.07 s | 605,600 KiB | 1,716,868 checked rows across 15 validator groups |
| CSV/JSON/SQL export and SQLite seed verification | 27.46 s | 1,062,368 KiB | Includes `seed.sql`, fresh `seed.db`, row-count checks, and SQLite validation |
| Total measured stages | 73.09 s | ~1.04 GiB peak | Sequential stages; maximum of the stage RSS values |

An export-time hotspot in event-snapshot scrubbing was avoided by checking for label-key substrings before parsing JSON. The generator now writes only the requested scale (it no longer generates the opposite scale just to print a second coverage report), and CLI post-generation validation runs in a separate process so the generator's pandas frames do not overlap with the validator's table-loading memory. Timings are measurements from this environment; other machines vary with storage throughput and memory.
