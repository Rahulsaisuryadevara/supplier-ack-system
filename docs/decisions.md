# Design decisions, assumptions, trade-offs, and limitations

This log describes the current implementation. The schema source of truth is `src/supplier_ack/schema.py`; generator parameters are in `config/generator_config.yaml`; runtime policy is shared under `src/supplier_ack/rules/`.

## Design decisions

| # | Decision | Alternatives considered | Trade-off | Reason |
|---:|---|---|---|---|
| 1 | **Python 3.11+** for the application and CLI. | Java/.NET service; notebook-only prototype. | Less raw throughput than compiled services, but low friction and a mature data/test ecosystem. | The challenge emphasizes explainable logic, synthetic data, and verifiable outcomes over deployment infrastructure. |
| 2 | **pandas + NumPy Generator** for tabular generation and analysis. | Hand-built row objects; Faker/global random state; database-first generation. | DataFrames are concise and measurable but use substantial RAM at full scale; one RNG stream means generation-order changes can change downstream samples. | Supports explicit schemas, distributions, summaries, and reproducible seeded generation. |
| 3 | **SQLite** for durable runtime state and reviewer seed database. | PostgreSQL/MySQL server; in-memory dictionaries; flat CSV-only storage. | Simple zero-service setup and real FK/transaction support; write concurrency and database size are not suited to high-volume multi-user production. | A portable local database is enough to demonstrate transactionality, constraints, event history, and approval gating. |
| 4 | **argparse** for the unified CLI. | Typer/Click; separate scripts per operation. | More manual help/argument wiring, but no extra runtime CLI dependency and one consistent entry point. | Copy-pasteable commands are part of the review and demo workflow. |
| 5 | **One shared rule library** for generator and runtime (`rules/thresholds.py`, `rules/derived.py`, `rules/impact.py`). | Duplicate business rules in generator and runtime; database-only stored procedures. | Shared pure functions couple both paths to the same policy API, so changes must preserve compatibility. | Prevents generated history and live event processing from disagreeing about thresholds, statuses, and derived values. |
| 6 | **Supplier silence means no acknowledgement row.** It is represented by a PO with no ACK plus a silence report/chase request. | Fabricate a `NO_RESPONSE` acknowledgement; store only a boolean on the PO. | Queries need a left join or explicit silence report; avoids confusing absence of response with an actual supplier-submitted event. | Absence is the business fact. The chase is an operational event, not a fabricated supplier response. |
| 7 | **Revision history uses full-row snapshots and parent-scoped revision IDs.** New ACK/promise/plan versions are appended; current/superseded flags identify effective versions. | In-place mutation of one current row; storing only a delta patch. | More storage and repeated fields, but each revision is independently interpretable and auditable. | Preserves what was known/committed at each point and supports stale-revision detection. |
| 8 | **Approval thresholds are configurable and inclusive.** Defaults: price change 5%; date slip 7 calendar days; quantity change 10%; hard limits: 15%, 30 days, and 50%, respectively. | Always-manager approval; thresholds inferred from the sample; strict-exclusive boundaries. | Thresholds are policy defaults rather than empirically optimized business policy; exact boundaries require tests. | Provides understandable planner autonomy, manager escalation for material changes, and deterministic rejection for hard-limit breaches. |
| 9 | **Escalation is role-based and explicit.** Within ordinary thresholds routes to Planner; beyond threshold requires Operations Manager; hard-limit breaches are rejected. | Random approval outcomes; single approver for every request; silently accept hard-limit changes. | Can leave a request pending when no eligible approval event exists; escalation adds decision rows and workflow states. | Decisions remain reproducible, attributable, and safe to apply only after the required approval level. |
| 10 | **Anomalies are injected after a clean baseline and labelled in separate ground truth.** | Corrupt data silently; put labels in input rows; rely only on naturally occurring anomalies. | Ground-truth labels are a separate sensitive evaluation target and require leakage checks; synthetic anomalies do not represent all real-world failure modes. | Enables deterministic detector evaluation without contaminating model inputs, while retaining an auditable expected outcome. |
| 11 | **Approval IDs embed the complete parent ChangeRequest ID:** `APR-<change_request_id>-NN`. | Global numeric approval IDs; short ID containing only a sequence. | IDs can be long and repeat parent text, but can be interpreted without a lookup and remain unambiguous across requests. | The parent relationship is visible in exported files and logs; counters fail on overflow rather than silently changing format. |
| 12 | **Determinism uses seed `20261022`, one injected NumPy RNG, fixed config, deterministic IDs, and seeded business dates.** | Independent global RNGs; wall-clock timestamps; random UUIDs. | A code/config/dependency change can intentionally change checksums; a single stream makes draw order part of the reproducibility contract. | Same-seed output can be compared byte-for-byte; a different-seed counter-test proves the seed has an effect. Runtime processing timestamps are real operational metadata and are not part of generated historical records. |
| 13 | **Derived values have one implementation in `rules/derived.py` and reconciliation is a hard gate.** | Compute values inline in each generator; store unverified hand-authored totals. | The shared module is a dependency across generation, validation, and reporting; updates need targeted regression tests. | Prevents formula drift for totals, quantity/price deltas, acknowledgement status, promise lateness, projected supply, and performance metrics. |
| 14 | **InventoryPlan is versioned and approval-gated.** Baseline v1 exists for each line; accepted acknowledgement-only promises can project through their defined path, while ChangeRequest-driven projections require the correct approval. | Update a single plan row; apply changes on request submission; optimistically apply then compensate. | Append-only versions increase row counts and conservative gating can hold safe-but-unrelated changes while another change is unresolved. | Prevents pending/rejected changes from silently altering available supply and leaves a clear audit trail. |
| 15 | **Append-only `entity_event` stores previous/new state snapshots.** | Mutable audit rows; external log only; event sourcing with no current-state snapshots. | Snapshot payloads consume storage and require event/schema version discipline, but improve traceability and replay. | Reviewers can see both the change and its before/after context; update/delete triggers protect the log. |
| 16 | **SQLite FK enforcement and relationship-consistency triggers are enabled explicitly.** | Rely on application checks alone; assume SQLite FK defaults. | Connections must enable `PRAGMA foreign_keys=ON`; some business checks still live in Python because they span derived or temporal logic. | Rejects broken references close to storage and demonstrates relational integrity. |
| 17 | **Downstream impact is calculated from source plan/order values and explicit tolerances.** | Randomly label impacted orders; infer impact from PO status alone. | Deterministic thresholds simplify interpretation but cannot model every production scheduling constraint. | Impact rows and severity/status changes can be independently checked against their inputs. |
| 18 | **Role-targeted notifications use a recipient bridge and trace traversal.** | One free-text recipient field; broadcast all notices to all actors. | More tables and joins, but supports multiple recipients, role correctness, and a complete trace chain. | Notifications must be actionable and attributable rather than merely present. |
| 19 | **pytest + pytest-cov** is the verification framework; unit, integration, slow, and e2e tests are separated by markers. | Manual-only verification; one monolithic end-to-end test; alternate test framework. | Subprocess and full-scale tests are slower; aggregate coverage depends on which marked tests were actually run. | Regression checks are repeatable, and coverage gaps can be reported honestly instead of implying that a demo alone proves correctness. |
| 20 | **CSV is the transparent interchange format; JSON and SQLite SQL/DB are supplementary exports.** | Binary-only database; JSON-only export; external warehouse. | Multiple formats cost disk and export time and must be kept consistent. | CSV is reviewable in common tools, JSON supports structured consumers, and SQL/SQLite demonstrates relational loading and constraints. |

## Assumptions

The challenge statement leaves some operational details open. These assumptions make the prototype executable and are policy choices, not claims about YottaFlex's real processes.

1. **Synthetic-only data:** all suppliers, people, items, dates, purchase orders, and outcomes are generated; no production supplier feed or personal data is required.
2. **Calendar-day date slips:** date thresholds use calendar days, not business days or a regional holiday calendar.
3. **Inclusive threshold boundary:** a delta exactly equal to the planner threshold remains within the threshold. Tests pin this behavior.
4. **Percentage delta:** price and quantity deltas are calculated relative to the old/source value; a zero or invalid baseline is handled by the rule implementation rather than guessed by a caller.
5. **Event budget definition:** configured `event_count` is ACK revision rows plus ChangeRequest rows, not all database rows or `entity_event` records. Silence has no ACK row.
6. **Silence observation date:** the configurable fixed `coverage.as_of_date` anchors overdue-silence classification, avoiding wall-clock-dependent generated datasets.
7. **Planner ownership:** each PO has one owning planner actor; that owner receives relevant workflow notices. Logistics/operations recipients are selected by event type and policy.
8. **Approval levels:** the planner can approve within-threshold changes; the operations manager is required for changes outside planner thresholds but within hard limits. Changes beyond hard limits are rejected.
9. **Conservative plan handling:** if an unresolved/rejected change makes the line's effective supply ambiguous, retain the last safe projection rather than partially apply it.
10. **Downstream impact tolerances:** defaults are zero grace days and zero allowed quantity shortfall, configurable in YAML.
11. **Severity bands:** impact severity is determined from the implemented bands in `rules/impact.py`; it is a prioritization signal, not a calibrated financial risk model.
12. **Revision identity:** IDs encode a fixed challenge year (`2026`) and parent-scoped revision counters. They are identifiers, not timestamps.
13. **Runtime timestamps:** generated historical records must be deterministic; actual runtime events may use wall-clock processing timestamps because they represent live execution.
14. **Starter/full comparability:** both scales share the same functions and rules; counts/distributions are controlled by config. Exact child row counts can vary if seed or configuration changes.
15. **Detector evaluation:** the four required injected anomaly classes define the measured detector target. Perfect performance on this controlled cohort does not establish performance on unseen production data.

## Limitations

- No hosted demo, web interface, API service, or multi-tenant deployment.
- No authentication, authorization server, secrets vault, or production identity integration. Role checks are workflow/domain rules, not a security boundary.
- The runtime is a single-user local CLI backed by SQLite. SQLite is not intended for high-concurrency distributed writes or unbounded warehouse-scale data.
- No live supplier portal, EDI/API integration, email/SMS delivery, carrier tracking, ERP/MRP connector, or actual notification dispatch. Notifications are generated/stored artifacts.
- No real supplier data, calibrated business thresholds, real holiday calendar, probabilistic lead-time forecast, or optimization solver for production rescheduling.
- Rule-based detectors are deliberately narrow and evaluated against synthetic labelled cases; no trained ML model is included.
- Full-scale generation/export is memory and disk intensive (roughly 1.04 GiB peak RSS in the measured environment for the measured pipeline stages). Performance varies by machine and dependency versions.
- Runtime operational timestamps are not deterministic across executions. Deterministic checksum comparisons apply to generated outputs under a fixed environment/configuration, not live runtime databases or manifests containing operational metadata.
- Coverage is not 100%. The recorded 55% figure came from a focused coverage run, not the full suite; the previous constrained execution could not establish trustworthy aggregate full-suite coverage. Run `pytest` locally for current full-suite coverage.
- Full scale is not part of every routine test run. The starter scale is used for practical fast feedback; full-scale checks should be run separately where resources allow.

## Next steps

1. Add a hosted read-only demo or small API/UI after defining an authentication and data-retention model.
2. Replace local SQLite with PostgreSQL if concurrent users, centralized audit, or production volume require it; preserve the current schema and event contracts.
3. Add connector adapters for supplier portal/EDI, ERP/MRP, carrier status, and real notification delivery behind tested interfaces.
4. Calibrate thresholds and severity against approved business policy and historical outcomes; include business-day calendars and explicit timezone rules.
5. Extend detector evaluation with unseen/held-out cases and false-positive analysis before considering statistical or ML models.
6. Expand tests for less-covered export, workflow, detector, and reporting branches; run full suite and full-scale performance checks in CI with documented resource limits.
7. Add migration/versioning policy for schema and event payload evolution, plus backup/recovery and access-control controls before production use.
8. Define service-level objectives, operational monitoring, retention, and incident-response procedures before hosting.
